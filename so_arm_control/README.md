# SO-ARM Control

The `ros2_control` setup for the SO-ARM100 family: the joint trajectory controller, Pinocchio-based Cartesian IK teleop with self-collision checking, gripper control, and the launch files that bring it all up on real hardware or in the MuJoCo simulation.

## Contents

| Path | Purpose |
|------|---------|
| `launch/control.launch.py` | The control stack: `robot_state_publisher`, controller manager, `so_arm_controller`, `joint_trajectory_bridge` |
| `launch/teleop.launch.py` | Joystick/GUI Cartesian IK teleop, gripper control, and the support nodes below |
| `config/urdf_config.yaml` | Servo serial port, motor IDs, PID coefficients, mock mode |
| `config/control.yaml` | Controller manager (50 Hz) and `so_arm_controller` (joint trajectory) |
| `config/teleop.yaml` | Joystick buttons/axes, `teleop_ik_node` parameters, toggle and target-visualizer wiring |
| `config/joint_trajectory_bridge.yaml` | The collision-checked bridge all control paths route through |
| `config/so100.srdf`, `so101.srdf` | Self-collision link-pair exclusions (generated by `generate_srdf.py`) |
| `so_arm_control/` | The nodes: `teleop_ik_node`, `joint_trajectory_bridge_node`, `joint_state_switch_node`, `bool_toggle_node`, `target_visualizer_node`, run as `teleop_support_node` |
| `so_arm_control/so_arm_utils/` | Shared IK, self-collision (FCL), QoS and URDF-parsing helpers |
| `scripts/bootstrap_external_deps.sh` | Installs the collision checker's native/pip dependencies |

## Requirements

- ROS 2 Kilted or Jazzy with `ros2_control`, `ros2_controllers` (`joint_state_broadcaster`, `joint_trajectory_controller`), `joy` and `joy_teleop`.
- [`sts_hardware_interface`](https://github.com/adityakamath/sts_hardware_interface), built separately anywhere in this workspace's `src/`.
- [Pinocchio](https://github.com/stack-of-tasks/pinocchio) (`sudo apt install ros-kilted-pinocchio`) for the IK solver.
- `python-fcl` and `numpy-stl` (pip) for self-collision checking — install with `./scripts/bootstrap_external_deps.sh`. If missing, `joint_trajectory_bridge` logs an error and disables the check instead of crashing.
- `so_arm_description` for the robot model.
- For `ros2_control_hardware_type:=mujoco`: `so_arm_mujoco`, [`mujoco_ros2_control`](https://github.com/ros-controls/mujoco_ros2_control) and `mujoco_ros2_control_plugins` (`sudo apt install ros-kilted-mujoco-ros2-control ros-kilted-mujoco-ros2-control-plugins`), and [`mujoco_ros2_plugins`](https://github.com/adityakamath/mujoco_ros2_plugins) for the simulated `/emergency_stop` (not vendored — see the [repository README](../README.md#simulation-optional)).

## Running

```bash
ros2 launch so_arm_control control.launch.py                                        # so101, real hardware
ros2 launch so_arm_control control.launch.py model:=so100                           # so100
ros2 launch so_arm_control control.launch.py use_mock:=true                         # no hardware, simulated motors
ros2 launch so_arm_control control.launch.py ros2_control_hardware_type:=mujoco     # MuJoCo
ros2 launch so_arm_control control.launch.py ros2_control_hardware_type:=mujoco mujoco_arena:=true  # + cubes/tray
ros2 launch so_arm_control teleop.launch.py                                         # joystick/GUI teleop, on top of control
```

`so_arm_bringup` normally starts both together. The `joy` node is not started for you — run `ros2 run joy joy_node` on whichever machine has the controller plugged in.

### Launch arguments

| Argument | Default | Meaning |
|----------|---------|---------|
| `model` | `so101` | `so100` or `so101` |
| `serial_port` | `""` | Serial port; empty uses the xacro default (`/dev/ttySERVO`) |
| `use_mock` | `""` | `true`/`false`; empty uses the xacro default (`false`) |
| `use_sim_time` | `false` | Use `/clock` from a simulator |
| `ros2_control_hardware_type` | `real` | `real` or `mujoco` |
| `mujoco_headless` | `false` | `mujoco` only: suppress the viewer window |
| `mujoco_arena` | `false` | `mujoco` only: `true` adds a small tabletop workspace within reach - three graspable cubes and a tray - on top of the default flat skybox+floor scene |
| `frame_prefix` | `""` | Prefix for every published TF `frame_id` (e.g. `leader/`); empty for the single-arm default |
| `wrist_camera_urdf` | `true` | SO101 only: `false` omits the wrist camera mount/links/joints from `robot_description` |

`teleop.launch.py` takes one argument, `frame_prefix`, which must match whatever `control.launch.py` was given.

## Configuration

**`urdf_config.yaml`** holds the servo serial port (`/dev/ttySERVO`), baud rate, per-joint motor IDs (1–6, kinematic order), operating mode, per-joint PID coefficients (default 14 / 24 / 0) and the position deadband. `serial_port` and `use_mock` can also be set on the launch command line; edit the file for the rest.

**`control.yaml`** sets the controller manager (50 Hz) and `so_arm_controller` (a `JointTrajectoryController` driving all six joints together, position + velocity interfaces).

**`teleop.yaml`** maps the joystick (a Steam Deck; see the [repository README](../README.md#joystick) for the buttons), and configures `teleop_ik_node` (end effector link, publish rate, `max_acceleration`, `max_target_reach`, and the experimental `effort_gain` — see the [repository README](../README.md#gripper-compliance-experimental-untested)).

**`joint_trajectory_bridge.yaml`** is the single point every control path (teleop, GUI sliders, replay) funnels through on its way to the controller. `enable_self_collision_check`, `collision_margin` and `intersection_margin` control the FCL-based check; a target that would self-collide is first clamped back to a collision-free boundary, and only dropped outright if no clamp resolves it.

## How it works

The launch file expands the URDF from `so_arm_description` with `urdf_config.yaml`'s values, starts one controller manager, and spawns `joint_state_broadcaster` and `so_arm_controller`. In `mujoco` mode, `mujoco_ros2_control`'s own control node runs the simulation in the same process instead of `ros2_control_node`, and additionally loads `so_arm_mujoco`'s `config/mujoco_ros2_control_plugins*.yaml` for a simulated `/emergency_stop` and (SO101 only) wrist camera — see [`so_arm_mujoco`'s README](../so_arm_mujoco/README.md#ros-simulation).

Joint commands take one path regardless of source: `teleop_ik_node` (Cartesian IK from the joystick or a GUI), GUI sliders, or replay all publish to `joint_commands_*` topics, `joint_state_switch_node` selects between them by priority (`replay` > `gui` > `ik`), and forwards the winner to `joint_trajectory_bridge_node`, which self-collision-checks it against the SRDF exclusions before publishing the actual `JointTrajectory`. The small support nodes run together in one process (`teleop_support_node`):

| Node | What it does |
|------|--------------|
| `bool_toggle_node` | Turns a joystick button press into a toggle: `/emergency_stop` and `/joint_state_switch` flip on each press, and stay in sync when the services are called from elsewhere |
| `joint_state_switch_node` | Selects between input sources by priority and republishes the winner |
| `target_visualizer_node` | Publishes an RViz marker for the IK target, colour-coded by active mode (record, e-stop, replay, GUI, IK teleop) |

While e-stopped, `teleop_ik_node` tracks the arm's live pose as its target instead of the pre-e-stop one, so releasing e-stop holds the arm where it was left by hand instead of snapping back.

## Using it with another payload or robot

`teleop.yaml` and `control.yaml` assume a single SO-ARM; a host robot embedding this arm (as `so_arm_bringup`'s leader-follower does) launches `control.launch.py` per arm with a distinct `frame_prefix`, and composes teleop separately. There is no payload macro here — `so_arm_description`'s URDF is the whole robot, not a module meant to mount on something else.

```bash
pytest test -q
```

Covers the collision-checked bridge and self-collision checker (FCL), the IK solver and motion limits, the toggle and mode-color logic, the launch files' arguments, and that the yaml configs agree with each other (joint names, topics).
